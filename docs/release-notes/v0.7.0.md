# v0.7.0

Three defects, each in a capability the parity ledger already graded green —
found by pointing Microsoft's own Python SDK at claims that until now rested
only on our tests. Independently-witnessed coverage went from 58% to 88% in
the process, but the coverage number is not the result; the bugs are.

**One behaviour change needs a decision: see Upgrading.**

---

## `nextLink` now resolves

Every list response carried a `nextLink` built from the vault's **canonical**
host, `https://{vault}.vault.azure.net`. That is correct for `id`, `kid`,
`sid` and `recoveryId` — real Key Vault returns exactly that, and the SDKs
depend on it. But `nextLink` is different in kind: it is a URL the client is
instructed to **fetch**. Against a localhost emulator the canonical host does
not resolve, so every Microsoft SDK's pager died on the second page:

```
ServiceRequestError: HTTPSConnection(host='emulator.vault.azure.net', port=443):
Failed to resolve 'emulator.vault.azure.net'
```

Links are now built from the host the caller actually addressed, while
identifiers stay canonical. If you list more than one page of secrets, keys or
certificates through any SDK, this release is the fix.

Our own tests parsed `nextLink` rather than following it, which is how a broken
pager stayed green through four releases.

## `nbf` / `exp` enforced on secret reads

A secret whose `nbf` had not arrived, or whose `exp` had passed, was returned
as though valid. Real Key Vault refuses with `403` — **not** `404`, so a caller
can tell "not yours yet" from "no such secret".

Keys deliberately differ and are unchanged: there only *cryptographic*
operations are refused while metadata reads stay permissive, because a key's
public half is not the secret. That asymmetry is Azure's, not ours.

## HSM key types are refused, not silently downgraded

`RSA-HSM` and `EC-HSM` were accepted and quietly turned into software keys —
the response even said `"kty": "RSA"`. A caller verifying "our keys are
HSM-backed" got a passing run and a false belief.

They are now refused with `400`, as a Standard-tier vault refuses them in
Azure; HSM-backed keys require Premium, whose guarantee is hardware this
emulator does not have. It is the same boundary already drawn for `oct`
(Managed HSM). This turns the ledger row from 🟡 Emulated to 🟢 Real by
becoming more faithful, not by softening the claim.

## Evidence

The Python witness suite grew from 31 checks to 45, covering secret
attributes, canonical object ids, the error envelope and `x-ms-request-id`,
paging, soft-delete conflict and `recoveryLevel`, key backup/restore, rotation
policy get/set, certificate backup, operation cancel/delete, the PKCS#10 CSR
from a named issuer, and delete cascading to the linked key and secret.

Fourteen claims that previously rested on our own client now carry a witness
driven by Microsoft's.

## Upgrading

**State now persists by default.** `KV_DATA_DIR` unset used to mean an
in-memory database; it now defaults to `./data`, so secrets, keys and
certificates survive a restart — the same posture as the rest of the emulator
family.

```
KV_DATA_DIR=          # explicitly empty: back to in-memory, nothing kept
```

*Unset* and *set-empty* differ deliberately. Containers are unaffected: the
image bakes `KV_DATA_DIR=/data`, and the compose files already set the empty
form so a throwaway stack leaves nothing behind.

Nothing else changes. If you page through lists with an SDK, you gain a fix;
if you relied on `RSA-HSM` being accepted, you now get the refusal Azure gives.
